## Carry-forwards opened during Sprint B

### `phase-4.5-chunk-2-route-mount-middleware-leak` (medium severity)

Opened during T10 spec review. Findings:

- Hono v4's `.route()` with overlapping mount paths shares middleware across sibling sub-routers (verified empirically during T10 spec review).
- In `apps/api/src/index.ts:57-59`, three sub-routers mount at `/logistics/pos`: `logisticsPosRouter`, `lpInboundRouter`, `dispatchCustomerLegRouter`. The first has a blanket `*` middleware that 403s anything except `role === "logistics"`.
- Result: the inline role allowlists in `dispatch-customer-leg.ts:40` (`["logistics","principal"]`) and `lp-inbound.ts:33` (`["logistics","principal","partner"]`) are partially dead — only `logistics` reaches them.
- Same pattern at `index.ts:54-55` for `logisticsOrdersRouter` + `resumeDispatchRouter`.
- Docstrings at `dispatch-customer-leg.ts:24-27` and `lp-inbound.ts:25-27` claim sibling-router middleware isolation — incorrect.

**Fix paths (pick one, deferred to a follow-up sprint):**
1. (a) Drop the redundant inline allowlists and treat the upstream blanket as the single source of truth (and update docstrings).
2. (b) Replace blanket `*` middleware with per-route middleware in `logisticsPosRouter`/`logisticsOrdersRouter` so siblings get clean middleware boundaries.
3. (c) Mount affected routers at non-overlapping paths.

**Severity rationale:** Medium. Not a security issue (more restrictive than intended — `principal` and `partner` are denied where the inline allowlist would have accepted them). But the advertised intent diverges from runtime behavior, which will trip the next person reading those docstrings.
