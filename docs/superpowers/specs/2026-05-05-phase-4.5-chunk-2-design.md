## 3. Per-leg LP schema split — option (b) (CQ1 locked)

### 3.1 Why option (b) wins

Three options were considered ((a) two columns on PO; (b) move customer-leg to thread; (c) hybrid with denorm). **Loo picked (b)** because:

- Maps cleanly to mental model: PO = "us → supplier" procurement document; thread = per-customer-order × per-supplier customer-leg state.
- Aligns with Chunk 1 spec C1.5 invariant: "PO scope = us → supplier ONLY".
- Removes the awkward Chunk 1 reality where customer-leg fields (RFD/accept timestamps from migration 0044) live on a procurement-leg table.

Trade-off acknowledged: ~50 reference points (36 in v3 RPCs + 7 Hono routes + 5 web files) need disambiguating. This is the largest scope item in Chunk 2.

### 3.2 Schema delta

```sql
-- Migration 0049: ADD COLUMNS on threads (additive, safe to roll forward).
ALTER TABLE order_supplier_threads
  ADD COLUMN IF NOT EXISTS delivery_partner_id      uuid REFERENCES delivery_partners(id),
  ADD COLUMN IF NOT EXISTS confirm_delivery_date    date,
  ADD COLUMN IF NOT EXISTS request_for_delivery_at  timestamptz,
  ADD COLUMN IF NOT EXISTS partner_accepted_at      timestamptz,
  ADD COLUMN IF NOT EXISTS partner_rejected_at      timestamptz;

-- Index for the same shape as 0044's PO partial index — supports Logistics
-- "RFD pending" queue queries by partner.
CREATE INDEX IF NOT EXISTS ost_rfd_pending_idx
  ON order_supplier_threads (delivery_partner_id, request_for_delivery_at)
  WHERE request_for_delivery_at IS NOT NULL
    AND partner_accepted_at IS NULL
    AND partner_rejected_at IS NULL;

-- Migration 0050: data migration — copy PO values to threads.
-- Each thread inherits its PO's customer-leg fields. NULLs stay NULL.
UPDATE order_supplier_threads t
   SET delivery_partner_id     = p.delivery_partner_id,
       confirm_delivery_date   = p.confirm_delivery_date,
       request_for_delivery_at = p.request_for_delivery_at,
       partner_accepted_at     = p.partner_accepted_at,
       partner_rejected_at     = p.partner_rejected_at
  FROM purchase_orders p
 WHERE t.po_id = p.id
   AND t.delivery_partner_id IS NULL;  -- idempotent re-run guard

-- Migration 0051: column rename + drops on PO (IRREVERSIBLE).
-- Run AFTER all RPCs + UI are rewritten to read from threads.
ALTER TABLE purchase_orders
  RENAME COLUMN delivery_partner_id TO procurement_partner_id;

ALTER TABLE purchase_orders
  DROP COLUMN IF EXISTS confirm_delivery_date,
  DROP COLUMN IF EXISTS request_for_delivery_at,
  DROP COLUMN IF EXISTS partner_accepted_at,
  DROP COLUMN IF EXISTS partner_rejected_at;

-- Drop the now-stale partial index from 0044 too.
DROP INDEX IF EXISTS po_rfd_pending_idx;
```

**Migration ordering rule**: 0051 (irreversible drops on PO) MUST land AFTER the RPC rewrite migration (call it 0055 — see §3.4) so no in-flight code reads the dropped columns. Plan executor enforces this via task dependencies.

### 3.3 RPC rewrites (~36 reference points across 0045)

The 8 RPCs in `0045_logistics_rpcs_chunk1.sql` that read/write `purchase_orders.delivery_partner_id` or the RFD/accept fields fall into two buckets:

**Procurement-leg RPCs (rename column reference only):**
- `logistics_assign_partner_and_dispatch` (0034:1) — sets `procurement_partner_id` instead of `delivery_partner_id` for factory_pickup flow.
- `lp_accept_inbound_delivery` / `lp_reject_inbound_delivery` (0045) — these are the LP confirming PO arrival at warehouse, which is procurement-leg → reads `procurement_partner_id`.

**Customer-leg RPCs (rewrite to read from thread):**
- `logistics_dispatch_customer_leg` (0045:480) — currently sets PO.request_for_delivery_at. Rewrite to write thread row instead. Takes `p_thread_id` not `p_po_id` going forward (signature change).
- `logistics_partner_accept_rfd` / `logistics_partner_reject_rfd` (0045) — same pivot to thread.
- `logistics_resume_dispatch_from_waiting` (0045) — reads RFD state → reads thread fields.

**Both legs (mixed)**:
- `logistics_receive_po_with_do` (0045:614) — receive is procurement-leg (PO arriving at wh), but it also advances threads → reads `procurement_partner_id` for partner-role gate, advances thread state, no customer-leg writes.

The plan's task list will dependency-order these such that 0051 (irreversible PO column drops) only runs AFTER all callers are rewritten and tests are green.

### 3.4 Single Chunk 2 RPC migration

Land all RPC rewrites in `supabase/migrations/0055_logistics_rpcs_chunk2.sql` using the same `CREATE OR REPLACE` self-contained-body pattern as 0045. Migration order:

```
0049 → ADD COLUMNS on threads
0050 → data migration (copy PO → thread)
0055 → CREATE OR REPLACE all RPCs reading new shape (no column drops yet)
       (after 0055 is applied + apps deployed, RPCs read from thread, but PO
        still has the old columns as dead weight)
0051 → rename procurement_partner_id + DROP customer-leg columns from PO
```

Note: 0051 numbered before 0055 lexically but applied AFTER. Migration framework runs by name (numeric) order — to control runtime ordering we must renumber. Final order:

```

0050_threads_customer_leg_backfill.sql
0051_logistics_rpcs_chunk2.sql           ← was "0055"
0052_purchase_orders_drop_customer_leg.sql ← was "0051"
```

Renumbered to match runtime order.

### 4.3 Multi-supplier orders

A customer order spanning multiple suppliers (e.g. mattress + sofa) surfaces in BOTH supplier tabs. The thread model from 0033 already supports this — each (order_id × supplier_id × category) is its own thread.

Per-tab list query:
```ts
qk.logistics.procurement(slug) → ['logistics', 'procurement', slug]
```
Calls a new endpoint `GET /api/logistics/procurement/{slug}` that filters `purchase_orders` + threads by supplier slug.

### 4.5 Slug source

The 3 slugs (`nice-future`, `hookka-sofa`, `hookka-bedframe`) are computed from `(supplier.slug, supplier_category)` per migration 0032. But Sofa-vs-Bedframe under HoOKkA needs a category disambiguator since both share `supplier.slug = 'hookka'`. The tab slug is `{supplier_slug}-{category}` (matches the routing matrix).

Add a `RouteSupplierSlug` enum in `packages/shared/src/sops.ts` mirroring SUPPLIER_SOP keying:
```ts
export const PROCUREMENT_TAB_SLUGS = ['nice-future', 'hookka-sofa', 'hookka-bedframe'] as const;
export type ProcurementTabSlug = typeof PROCUREMENT_TAB_SLUGS[number];
```

Sidebar nav link (`PrincipalSidebar` / `LogisticsSidebar`) defaults to `nice-future`.

## 5. 4.5f — Stockpile alert + suggested replenishment (CQ2 locked: extend stock_balances)

### 5.1 Schema delta

```sql
-- Migration 0053: stockpile thresholds
ALTER TABLE stock_balances
  ADD COLUMN IF NOT EXISTS low_threshold  int CHECK (low_threshold IS NULL OR low_threshold >= 0),
  ADD COLUMN IF NOT EXISTS high_threshold int CHECK (high_threshold IS NULL OR high_threshold >= 0);

-- Optional: assert high >= low when both present.
ALTER TABLE stock_balances
  ADD CONSTRAINT stock_balances_threshold_order
    CHECK (low_threshold IS NULL OR high_threshold IS NULL OR high_threshold >= low_threshold);
```

NULL = "no alert configured for this (sku, warehouse)". Most rows start NULL; logistics admin sets thresholds via a new "Set thresholds" dialog on the Warehouse page (Phase 4 baseline).

### 5.2 Alert state computation

Computed at query time (no trigger / materialized view — keeps it simple):

```sql
-- New RPC logistics_stock_alerts() returns rows where
-- (qty - reserved) < low_threshold (i.e. effective stock below alert line).
CREATE OR REPLACE FUNCTION public.logistics_stock_alerts()
RETURNS SETOF (
  sku text,
  warehouse_id uuid,
  qty int,
  reserved int,
  effective int,
  low_threshold int,
  shortage int
)
...
```

Surfaces in:
- LogisticsDashboard alert tile (count of rows at/below threshold)
- LogisticsWarehouse page: red dot indicator on rows below threshold + "Set Threshold" inline edit

### 5.3 Suggested replenishment

Reads `logistics_awaiting_stock_shortage` (existing) AND `logistics_stock_alerts` (new), unions per-SKU, suggests qty = `(high_threshold || low_threshold * 2) - effective`. Surfaces as "Suggest from alerts" button in CreatePOModal (extends the existing "Auto-fill from awaiting stock" button — same UI pattern).

### 5.4 Components

- New: `apps/web/src/pages/logistics/components/SetThresholdDialog.tsx` (warehouse page row inline trigger)
- Extend: `apps/web/src/pages/logistics/components/CreatePOModal.tsx` — "Suggest from alerts" toggle alongside existing Stockpile mode
- Extend: `apps/web/src/pages/logistics/LogisticsDashboard.tsx` — Stock alerts tile

## 6. M4.6 — PO COGS source (CQ3 locked: backfill NULL)

### 6.1 Schema delta

```sql
-- Migration 0054: COGS columns + enum
CREATE TYPE cost_source_enum AS ENUM ('hand_entered', 'prev_po', 'system_suggested');

ALTER TABLE purchase_order_lines
  ADD COLUMN IF NOT EXISTS cost numeric(14,2) CHECK (cost IS NULL OR cost >= 0),
  ADD COLUMN IF NOT EXISTS cost_source cost_source_enum;

-- No backfill — legacy 0019/0025-era rows stay NULL.
-- New POs enforce non-NULL via zod schema + RPC raise.
```

### 6.2 zod + RPC enforcement

```ts
// packages/shared/src/schemas/logistics.ts — extends createPoInput.lines[]
const lineWithCost = z.object({
  sku: z.string().min(1),
  qty: z.number().int().positive(),
  cost: z.number().nonnegative(),                              // required for new POs
  costSource: z.enum(['hand_entered', 'prev_po', 'system_suggested']),
});
```

```sql
-- logistics_create_po + logistics_create_pos_batch RPCs add validation:
IF p_cost IS NULL OR p_cost_source IS NULL THEN
  RAISE EXCEPTION 'cost + cost_source required'
    USING ERRCODE = '22023', DETAIL = 'cost_required';
END IF;
```

### 6.3 UI flow

CreatePOModal:
- Each line gets cost input + cost_source dropdown
- "Source = prev_po" auto-fills cost from `logistics_recent_po_cost(sku)` RPC (new — returns last received PO line cost for same SKU, or NULL)
- "Source = system_suggested" auto-fills from a heuristic (TBD: maybe 110% of prev_po if available, else require hand-enter)

### 6.4 Finance reconciliation

Out of Chunk 2 scope (lives in Phase 5). Chunk 2 only ships the data; Phase 5 reads it. Keeping `cost_source` enum visible in PO list (column or hover-card) so logistics has audit transparency.
