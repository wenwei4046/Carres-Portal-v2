## 3. Data model changes

### 3.1 `product_skus.supplier_id` (new NOT NULL FK)

```sql
-- Migration 0026_product_skus_supplier_id.sql
ALTER TABLE product_skus ADD COLUMN supplier_id uuid REFERENCES suppliers(id);

-- Backfill from suppliers.cat_covered (one-time):
UPDATE product_skus ps SET supplier_id = (
  SELECT s.id FROM suppliers s
  WHERE split_part(ps.sku, ':', 1) = ANY(s.cat_covered)
  LIMIT 1
);
-- Verify no NULLs:
DO $$ BEGIN
  IF EXISTS (SELECT 1 FROM product_skus WHERE supplier_id IS NULL) THEN
    RAISE EXCEPTION 'Backfill incomplete — % rows still NULL',
      (SELECT count(*) FROM product_skus WHERE supplier_id IS NULL);
  END IF;
END $$;

ALTER TABLE product_skus ALTER COLUMN supplier_id SET NOT NULL;

-- Index for routing lookups
CREATE INDEX product_skus_supplier_id_idx ON product_skus(supplier_id);
```

**Why NOT NULL**: Loo locked "every SKU must have explicit supplier" — eliminates the cat_covered ambiguity bug where a SKU could match multiple suppliers.

**Backward compat**: `cat_covered` column on `suppliers` stays for now (read-only, used by old auto-route logic during migration). Drop in v3-S6 after all callers switch.

## 4. State machines (SOPs)

### 4.1 SOP_STANDARD

Used by: **Nice Future Mattress**, **HoOKkA Bedframe**, future supplier-categories with stockable inventory.

```
                  ┌──────────────────────────┐
                  │ awaiting_logistics_action│  ← entered after Confirm at proceed_request
                  └────────┬─────────────────┘
                           │ Logistics issues PO
                           │ (or auto-skip if stock available — see §4.4)
                           ▼
                  ┌──────────────────────────┐
                  │ ready_to_dispatch        │  ← entered after Receive PO + DO upload
                  │ (stock secured, reserved)│      → stock_balances += received qty
                  └────────┬─────────────────┘
                           │ Logistics assigns delivery partner
                           ▼
                  ┌──────────────────────────┐
                  │ dispatched               │
                  └────────┬─────────────────┘
                           │ Partner attaches POD DO
                           ▼
                  ┌──────────────────────────┐
                  │ delivered                │  ← stock_balances PHYSICALLY deducts here
                  └──────────────────────────┘
```

### 4.2 SOP_SOFA_SPECIAL

Used by: **HoOKkA Sofa** (and any future supplier-category that ships customer-direct without our warehouse staging).

```
                  ┌──────────────────────────┐
                  │ awaiting_logistics_action│
                  └────────┬─────────────────┘
                           │ Logistics issues PO
                           │ (PO sup_status = pending)
                           ▼
                ┌─────────────────────────────────┐
                │ HoOKkA produces; presses        │
                │ "Ready Confirm to Delivery"     │
                │ (sup_status = ready_confirm_sent│
                └────────┬────────────────────────┘
                         │ Partner sees task → contacts customer
                         ▼
              ┌──────────────────────────┐    ┌────────────────────────────┐
              │  Customer OK             │    │  Customer says NO          │
              │  Partner: Confirm Receive│    │  Partner: Reject to Receive│
              │  → partner_confirmed     │    │  → customer_rejected       │
              └────────┬─────────────────┘    └────────────┬───────────────┘
                       │                                   │
                       │ HoOKkA ships to                   │ Logistics gets task:
                       │ partner WH                        │ "Relocate Warehouse"
                       │ (sup_status=delivered             │ → picks new WH (own)
                       │  at partner WH)                   │ → sup_status=relocated
                       │                                   │ HoOKkA sees new dest
                       ▼                                   ▼
              ┌──────────────────────────┐    ┌────────────────────────────┐
              │ dispatched (at partner WH│    │ HoOKkA ships to own WH     │
              │  awaiting last-mile)     │    │ → sup_status=at_own_wh_    │
              │                          │    │   waiting                  │
              └────────┬─────────────────┘    │ → logistics_stage=waiting  │
                       │                      └────────────┬───────────────┘
                       │ Partner picks up + delivers       │
                       │                                   │ Customer's new date arrives
                       ▼                                   │ → Partner picks up from
              ┌──────────────────────────┐                 │   own WH → delivers
              │ delivered                │ ◄───────────────┘
              │ (POD DO attached)        │
              └──────────────────────────┘
```

**Key insight**: The "Waiting" stage exists ONLY in the customer-rejected sub-path. Happy-path sofa goes Awaiting Logistics Action → Dispatched → Delivered (no Ready to Dispatch, no Waiting).

### 4.3 SOP config (TypeScript hardcoded — Q4=B)

```ts
// packages/shared/src/sops.ts (NEW FILE)

import { z } from 'zod';

export type LogisticsStageV3 =
  | 'placed'
  | 'proceed_request'
  | 'awaiting_logistics_action'
  | 'ready_to_dispatch'
  | 'dispatched'
  | 'waiting'
  | 'delivered';

export type SopName = 'STANDARD' | 'SOFA_SPECIAL';

export interface SopDef {
  name: SopName;
  /** Stages visible in this SOP's kanban, in display order. */
  stages: LogisticsStageV3[];
  /** Allowed forward transitions (no-op if not present → block). */
  transitions: Array<{ from: LogisticsStageV3; to: LogisticsStageV3; rpc: string }>;
}

export const SOP_STANDARD: SopDef = {
  name: 'STANDARD',
  stages: ['awaiting_logistics_action', 'ready_to_dispatch', 'dispatched', 'delivered'],
  transitions: [
    { from: 'awaiting_logistics_action', to: 'ready_to_dispatch', rpc: 'logistics_receive_po_with_do' },
    { from: 'ready_to_dispatch',         to: 'dispatched',        rpc: 'logistics_assign_partner_and_dispatch' },
    { from: 'dispatched',                to: 'delivered',         rpc: 'logistics_attach_pod_do' },
  ],
};

export const SOP_SOFA_SPECIAL: SopDef = {
  name: 'SOFA_SPECIAL',
  stages: ['awaiting_logistics_action', 'dispatched', 'waiting', 'delivered'],
  transitions: [
    { from: 'awaiting_logistics_action', to: 'dispatched', rpc: 'logistics_partner_confirm_receive' },
    { from: 'awaiting_logistics_action', to: 'waiting',    rpc: 'logistics_relocate_warehouse' },
    { from: 'dispatched',                to: 'delivered',  rpc: 'logistics_attach_pod_do' },
    { from: 'waiting',                   to: 'delivered',  rpc: 'logistics_attach_pod_do' },
  ],
};

/** SUPPLIER × CATEGORY → SOP. */
export const SUPPLIER_SOP: Record<string, SopDef | { byCategory: Record<string, SopDef> }> = {
  // Use slugs for stability across env (the slug ↔ supplier_id is in seed.sql).
  'nice-future': SOP_STANDARD,
  'hookka':      {
    byCategory: {
      'sofa':     SOP_SOFA_SPECIAL,
      'bedframe': SOP_STANDARD,
    },
  },
};

/** Resolve SOP for a (supplier_slug, sku_category) pair. */
export function sopFor(supplierSlug: string, category: string): SopDef {
  const cfg = SUPPLIER_SOP[supplierSlug];
  if (!cfg) throw new Error(`No SOP for supplier ${supplierSlug}`);
  if ('byCategory' in cfg) {
    const sop = cfg.byCategory[category];
    if (!sop) throw new Error(`No SOP for ${supplierSlug}/${category}`);
    return sop;
  }
  return cfg;
}
```

- Transitions form a DAG (no cycles) per SOP
- Every SOP's `stages[0]` is `'awaiting_logistics_action'`
- Every SOP's last stage is `'delivered'`

### 4.4 Order routing matrix (Q1=A multi-tab visibility)

```
 customer order #100 (lines: 1×sofa, 1×bedframe, 1×mattress)
            │
            │ [proceed_order RPC]
            │
            ▼
   logistics_stage = proceed_request           (Total Order tab — sees full order)
            │
            │ [confirm_proceed_request RPC] — auto-detect:
            │   • if ALL lines have stock at any own WH → skip to ready_to_dispatch
            │   • else → split per supplier, each line → its supplier tab
            ▼
   ┌─ HoOKkA Sofa tab     (sees: 1×sofa,    state=awaiting_logistics_action, SOP_SOFA_SPECIAL)
   ├─ HoOKkA Bedframe tab (sees: 1×bedframe,state=awaiting_logistics_action, SOP_STANDARD)
   └─ Nice Future tab     (sees: 1×mattress,state=awaiting_logistics_action, SOP_STANDARD)
```

**Implementation**: `orders.logistics_stage` becomes a coarse rollup; per-(order, supplier_id, category) state lives on a NEW table:

```sql
-- Migration 0033_order_supplier_threads.sql (NEW table)
CREATE TABLE order_supplier_threads (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id        uuid NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
  supplier_id     uuid NOT NULL REFERENCES suppliers(id),
  category        text NOT NULL,        -- e.g. 'sofa', 'bedframe', 'mattress'
  sop_name        text NOT NULL,        -- 'STANDARD' | 'SOFA_SPECIAL'
  logistics_stage logistics_stage NOT NULL,
  po_id           uuid REFERENCES purchase_orders(id),
  warehouse_id    uuid REFERENCES warehouses(id),
  reserved_at     timestamptz,
  delivered_at    timestamptz,
  history         jsonb DEFAULT '[]'::jsonb,
  UNIQUE (order_id, supplier_id, category)
);
CREATE INDEX ost_order_idx ON order_supplier_threads(order_id);
CREATE INDEX ost_supplier_stage_idx ON order_supplier_threads(supplier_id, logistics_stage);
```

Order's roll-up `logistics_stage` is computed from its threads:

```sql
CREATE OR REPLACE FUNCTION orders_rollup_stage(p_order_id uuid)
RETURNS logistics_stage LANGUAGE sql STABLE AS $$
  WITH t AS (SELECT logistics_stage FROM order_supplier_threads WHERE order_id = p_order_id)
  SELECT CASE
    WHEN NOT EXISTS (SELECT 1 FROM t) THEN 'placed'::logistics_stage
    WHEN (SELECT bool_and(logistics_stage = 'delivered') FROM t) THEN 'delivered'::logistics_stage
    WHEN (SELECT bool_and(logistics_stage IN ('dispatched','delivered','waiting')) FROM t) THEN 'dispatched'::logistics_stage
    WHEN (SELECT bool_and(logistics_stage IN ('ready_to_dispatch','dispatched','delivered','waiting')) FROM t) THEN 'ready_to_dispatch'::logistics_stage
    ELSE 'awaiting_logistics_action'::logistics_stage
  END;
$$;
```

(Replaces `orders.logistics_stage` direct reads — kept for backward compat but recomputed on every transition.)

### 4.6 Reserve semantic clarified

| Stage | `stock_balances.reserved` reflects what? | `stock_balances.qty` reflects what? |
|---|---|---|
| `placed`, `proceed_request` | nothing | physical stock |
| `awaiting_logistics_action` | nothing | physical stock |
| `ready_to_dispatch` | this order's qty (just reserved at Receive PO time) | physical stock (just incremented from received PO) |
| `dispatched` | this order's qty (still reserved) | physical stock (not yet shipped to customer) |
| `waiting` (sofa post-relocate path) | this order's qty | physical stock at own WH |
| `delivered` | nothing (released) | physical stock decremented |

## 6. Auto-detect Stock + Generate PO reform

### 6.1 The bug we ship-fixed earlier today (`cdb61ea`)

C5.3 endpoint computed `need vs available` but had no PO-existence filter. After Loo's reform, the bug becomes structural:

> Auto-fill should return **threads in `awaiting_logistics_action` whose `po_id IS NULL`** — i.e. orders that have been confirmed but not yet had a PO raised. Stock comparison is REMOVED from the auto-fill logic because reserve-on-confirm semantics are gone.

### 6.2 New endpoint contract

```ts
// GET /api/logistics/pos/auto-detect-orders-without-po?supplier_id=X&category=Y
// Returns threads ready for PO issuance, grouped per (supplier, category).

interface AutoDetectResponse {
  threads: Array<{
    thread_id: uuid;
    order_id: uuid;
    order_dl: number;
    customer_name: string;
    supplier_id: uuid;
    supplier_name: string;
    category: string;            // e.g. 'sofa'
    sku: string;
    qty: number;
    placed_at: timestamptz;
    delivery_date: date | null;
  }>;
  /** Aggregated for the modal's "Issue PO with these lines" pre-fill. */
  suggested_pos: Array<{
    supplier_id: uuid;
    supplier_name: string;
    category: string;
    lines: Array<{ sku: string; qty: number }>;
    dl_refs: number[];
  }>;
}
```

**SQL** (TS-side aggregation, mirrors the C5.3 pos.ts pattern but with the right filter):

```ts
const { data: threads } = await sb
  .from('order_supplier_threads')
  .select('id, order_id, supplier_id, category, ...')
  .eq('logistics_stage', 'awaiting_logistics_action')
  .is('po_id', null)              // ← THE KEY FILTER (vs C5.3 which had none)
  .filter(...)                    // optional supplier_id / category from query
  .order('placed_at');
```

Aggregation in TS: group by `(supplier_id, category)`, sum line.qty per SKU, build `suggested_pos`.

### 6.3 CreatePOModal flow change

The modal now has **two distinct entry points**:
- **From per-supplier tab "+ New PO"**: prefill is empty, user picks SKUs manually
- **From Procurement "+ Auto-fill"**: prefill is `suggested_pos[i]` (one or many supplier groups, fully populated)

When user clicks Issue PO with auto-fill prefill, the batch RPC (already shipped in C5.2 as `logistics_create_pos_batch`) fires, and each new PO links its `dl_refs` to the threads it covers + sets each thread's `po_id`.

### 6.4 Side effect: C5.3 endpoint deprecation

`GET /api/logistics/pos/awaiting-stock-shortage` (just shipped in `cdb61ea`):
- v3-S1: Keep alive but always returns `{shortage: []}` (no-op) so existing UI doesn't break
- v3-S2: Remove the route + the hook + the button (replaced by new auto-detect endpoint)

Tests for it: delete in v3-S2.

### 7.4 Stock balance increment

Inside `logistics_receive_po_with_do`:

```sql
-- For each received line:
UPDATE stock_balances
   SET qty = qty + p_received_qty
 WHERE warehouse_id = p_destination_warehouse_id
   AND sku = p_sku;

-- If the (warehouse, sku) row doesn't exist, INSERT it.
INSERT INTO stock_balances (warehouse_id, sku, qty, reserved)
SELECT p_destination_warehouse_id, p_sku, p_received_qty, 0
WHERE NOT EXISTS (SELECT 1 FROM stock_balances WHERE warehouse_id = p_destination_warehouse_id AND sku = p_sku);

-- Then reserve for the PO's covered threads:
UPDATE order_supplier_threads
   SET logistics_stage = CASE WHEN sop_name = 'SOFA_SPECIAL' THEN 'dispatched' ELSE 'ready_to_dispatch' END,
       warehouse_id = p_destination_warehouse_id,
       reserved_at = now()
 WHERE po_id = p_po_id;

-- Then increment reserved on stock_balances for each covered thread's line:
UPDATE stock_balances sb
   SET reserved = sb.reserved + th_line.qty
  FROM order_supplier_threads ost
  JOIN ... -- via order_lines
 WHERE ost.po_id = p_po_id
   AND sb.warehouse_id = p_destination_warehouse_id;
```

(Pseudo-SQL; real RPC handles edge cases like partial receive, multi-line POs, etc.)
