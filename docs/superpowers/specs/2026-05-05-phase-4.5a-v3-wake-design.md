## 1. Goal

Wake the v3 thread system in production by completing the full v2 → v3 vocabulary transition that v3 spec §3.3 + §17.4 originally pinned to "v3-S11". After this spec ships:

- All logistics RPCs write `awaiting_logistics_action` (never `awaiting_stock`)
- The FE kanban renders the stage as `awaiting_logistics_action` natively (column id renamed)
- The deprecated `awaiting_stock` enum value is dropped from the `logistics_stage` type
- v3 threads (created at confirm time) drive logistics stage via the `orders_rollup_stage()` trigger from 0036
- Auto-skip-from-stock behavior is restored: confirm-time stock-sufficient orders bypass the awaiting state and reserve directly into `ready_to_dispatch` (no ghost PO)

End state: v3 thread infrastructure is fully active. v2 enum/RPC vocabulary is retired.

### 4.3 v3 confirm auto-skip-from-stock branch

`logistics_confirm_proceed_request_v3` body (post-0039):

```text
1. Resolve order + lines + per-supplier groups (existing v3 logic)
2. INSERT order_supplier_threads rows with logistics_stage='awaiting_logistics_action'
   (existing v3 logic from 0034)
3. NEW: For each (sku_id, required_qty) across all freshly-created threads:
     SELECT sum(available_qty) FROM stock_balances WHERE sku_id = ?
     -> tally per-thread shortage
4. NEW: IF every thread has zero shortage:
     a. UPDATE order_supplier_threads
          SET logistics_stage = 'ready_to_dispatch'
        WHERE order_id = p_order_id;
     b. For each (sku_id, qty) consumed:
          INSERT stock_movements (kind='out', reason='reserve_from_buffer',
                                  sku_id, qty, order_id, ...)
          UPDATE stock_balances SET available_qty = available_qty - qty;
     c. orders_rollup_stage() trigger fires (0036): orders.logistics_stage = 'ready_to_dispatch'
   ELSE:
     leave threads at 'awaiting_logistics_action'; orders rolls up to same.
5. Return v3 confirm response (existing shape)
```

**No PO created** at auto-skip time. The audit trail is via `stock_movements.order_id` referencing the consuming order. The buffer PO that originally received this stock has its own past `stock_movements` row with `kind='in', reason='po_receive'`.

### 4.6 Pre-flight verification (mandatory before 0040 applies)

Before applying 0040, the implementation plan MUST verify:

1. `grep -rn "'awaiting_stock'::logistics_stage" supabase/migrations/` returns ZERO matches in non-historical files (i.e., post-0038/0039 RPC bodies are clean).
2. `grep -rn "'awaiting_stock'" apps/` returns ZERO non-test matches in code (FE + API code is clean).
3. Staging DB: `SELECT count(*) FROM orders WHERE logistics_stage = 'awaiting_stock'` returns 0 (per §17, already 0 since 0028 migrated all rows).
4. Staging DB: `SELECT count(*) FROM order_supplier_threads WHERE logistics_stage = 'awaiting_stock'` returns 0.
5. Identify all CASCADE casualties from `DROP TYPE logistics_stage CASCADE`:
   ```sql
   SELECT pg_describe_object(d.classid, d.objid, d.objsubid) AS object
   FROM pg_depend d
   WHERE d.refobjid = 'public.logistics_stage'::regtype
     AND d.deptype = 'n';
   ```
   Every row that returns must be reproduced in step 6 of 0040 (or earlier in the migration).

If any of 1–4 fails, abort and fix before applying 0040. If 5 surfaces unexpected dependencies, expand 0040's recreate block.

## 5. Test plan

### 5.1 Unit (vitest)

- `_v3_claim_threads_for_po` (already covered by 0037 tests; verify still passes after 0040)
- New auto-skip-from-stock branch in 0039:
  - All-sufficient case: stock covers all threads → all threads → `ready_to_dispatch`, stock_balances reduced, stock_movements written
  - Partial-sufficient case: one thread has shortage → all threads stay `awaiting_logistics_action` (no half-resolution; atomic)
  - Zero-stock case: equivalent to current v3 behavior (threads stay awaiting)
  - Concurrent reserve race: two confirms claiming same buffer → second errors with serialization_failure (FOR UPDATE on stock_balances)

### 5.2 Integration (vitest + msw)

- API callsite swap test for each of 5 RPCs: input → mocked SB response → assert correct response shape
- v3 confirm auto-skip path: end-to-end through `POST /api/logistics/orders/:dl/confirm-proceed`

### 5.3 E2E (Playwright)

- **Path A (stock sufficient)**: Login as logistics → existing dealer order at `proceed_request` → click Confirm → assert order moves to `ready_to_dispatch` column directly (skip awaiting_logistics_action). stock_balances UI shows reserved.
- **Path B (stock shortage)**: Login as logistics → existing dealer order with shortage → click Confirm → assert order lands in `awaiting_logistics_action` column. Auto-fill produces PO. After receive PO + DO, order moves to `ready_to_dispatch`.
- **Path C (mixed thread)**: Multi-supplier order, one thread has stock, other doesn't → assert ALL threads stay `awaiting_logistics_action` (atomic; no partial promotion).

### 5.4 Smoke test (manual on staging)

After 0038, 0039, 0040 applied to staging (in order, with verification gates):

- [ ] Login as logistics
- [ ] Existing demo order at `proceed_request` confirmed → assert correct stage
- [ ] DB query: `SELECT logistics_stage FROM orders WHERE id = ?` returns expected value
- [ ] DB query: `SELECT logistics_stage FROM order_supplier_threads WHERE order_id = ?` returns thread-level stages
- [ ] DB query: `SELECT enumlabel FROM pg_enum WHERE enumtypid = 'logistics_stage'::regtype` returns 7 values, no `awaiting_stock`

## 6. Rollback plan

| Migration | Reversibility | Action if reverted |
|---|---|---|
| 0038 | Reversible BEFORE 0040 only | Apply a 0038-revert migration that re-CREATEs OR REPLACES v2 RPC bodies (write `'awaiting_stock'`). API still works because column accepts both during transition (until 0040). After 0040 applied, this revert FAILS because the enum no longer has `awaiting_stock` — would need to recreate-add-value first. |
| 0039 | Reversible BEFORE 0040 only | CREATE OR REPLACE confirm RPC without auto-skip branch. Same constraint as 0038: post-0040 revert would not write `awaiting_stock` so still safe; but reverting auto-skip alone leaves auto-skip-from-stock unwired. Recommend revert + bug fix forward, not roll back. |
| 0040 | **NOT reversible** | Adding `awaiting_stock` back to enum requires another recreate-type migration; lossy because rows already migrated. **High-water mark**: only apply 0040 when 0038 + 0039 are validated stable on staging for ≥24h, AND no production rollback need has surfaced. |
| API callsite swap (orders.ts:471) | Trivially reversible | 1-line revert |
| FE column rename | Trivially reversible | 1-line revert (but FE then drifts from DB until next deploy) |

**Defensive ordering for production deploy**:
1. Apply 0038 to staging → verify all v2 RPCs still work, just write new value
2. Apply 0039 to staging → verify auto-skip path passes E2E
3. Soak 24h on staging
4. Apply 0040 to staging → verify enum has 7 values
5. Apply 0038 + 0039 + 0040 to production in same window

## 8. Open questions (carried into implementation plan)

- **OQ1**: For path C (mixed-thread atomicity), does v3 confirm rollback all stock reservations if one thread errors mid-loop? Implementation plan must use a single transaction OR compensating UPDATE.

- **OQ3**: FE test rename — is there an `awaiting_stock` literal in any non-test code path (e.g., conditional logic, label maps)? Plan must include a comprehensive grep audit before deciding scope.
- **OQ4**: Does `logistics_dispatch` / `logistics_attach_pod_do` / `logistics_assign_partner_and_dispatch` reference `awaiting_stock`? They probably don't (they operate on `ready_to_dispatch` / `dispatched`), but verify during plan.
