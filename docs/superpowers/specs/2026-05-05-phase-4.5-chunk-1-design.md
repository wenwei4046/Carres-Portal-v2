### 0.4 RLS reverse — `partner_updates_rfd_fields` is a TIGHTENING, not a NEW grant

0002:249 `po_scoped_update` already lets partner `UPDATE` any field on their assigned PO row (whole-row write). The drafted §6.6 `partner_updates_rfd_fields` policy reads as adding access — but in fact it's adding a **field-level whitelist on top**. To enforce the whitelist, we need a `RESTRICTIVE` policy (PostgreSQL 15+) or revoke + replace, otherwise 0002's permissive policy still wins.

**Action**: write `partner_updates_rfd_fields` as `AS RESTRICTIVE` so it AND-stacks with 0002 (row + column-level guard). Whitelist columns: `partner_accepted_at`, `partner_rejected_at`, `confirm_delivery_date`, `customer_rejection` (jsonb stamped on RFD reject). Tested via column-level grants OR trigger-based audit. (v3 update per Codex F10: dropped `partner_rejection_reason` from whitelist — column itself dropped.)

### 0.8 v3 — Codex outside-voice review fixes (2026-05-05 evening)

After v2 was written, `/plan-eng-review` ran Codex as an independent reviewer. Codex found **6 P0 schema bugs that would fail migration apply** + **3 P0 architectural issues** + **3 P1 issues**. All 12 verified against the actual schema (HEAD `84ac6be`). Fixes propagate into the relevant sections below; this subsection is the **change log**.

#### F1 — `partner_confirm_receive` advances threads to `dispatched` (P0 architectural)

0034:421-424 confirms: existing RPC sets `update order_supplier_threads SET logistics_stage = 'dispatched'`. **That's wrong for Loo's new Sofa pre-flight Accept** — pre-flight Accept means HoOKkA proceeds with planned delivery, NOT that delivery happened. Thread should stay at `awaiting_logistics_action` until Receive fires.

**Fix**: do NOT reuse `partner_confirm_receive`. Write a NEW `lp_accept_inbound_delivery` RPC that ONLY sets `sup_status='partner_confirmed', partner_confirmed_at=now()` and does NOT advance threads. Existing 0034 `partner_confirm_receive` becomes deprecated for the Sofa flow (kept callable for v3 backwards compat; carry-forward `phase-4.5-cleanup-old-partner-confirm-receive` opens). Reverses §0.3 RPC reuse decision for this one RPC.

#### F2 — 0036 rollup treats `waiting` as `dispatched` level (P0 architectural)

0036:91 confirms: `bool_and(logistics_stage in ('dispatched', 'delivered', 'waiting')) → 'dispatched'`. The original v3-S5 author treated `waiting` = post-relocate forward-progress. **Loo's new flow says `waiting` = at_warehouse_waiting = stock at wh waiting for customer date = NOT yet dispatched.**

**Fix**: NEW migration **0047_orders_rollup_stage_amend.sql** that `CREATE OR REPLACE`s `orders_rollup_stage()` to:
- `bool_and(logistics_stage in ('dispatched', 'delivered'))` → `'dispatched'` (drop `waiting` from this set)
- `bool_and(logistics_stage in ('ready_to_dispatch', 'dispatched', 'delivered', 'waiting'))` → `'ready_to_dispatch'` (`waiting` rolls up to `ready_to_dispatch`-level)

Net effect: a Sofa thread in `waiting` → order rolls up to `ready_to_dispatch` (not `dispatched`). The `at_warehouse_waiting` distinction surfaces via PO-level `sup_status` filter in Logistics page, not order-level rollup.

#### F3 — `sup_status='received'` is not a valid `po_sup_status` value (P0 schema)

0001 enum + 0030 additions list ALL `po_sup_status` values: `pending, acknowledged, in_production, shipped, delivered, ready_for_pickup, pickup_assigned, pickup_accepted, picked_up, reassign_needed, ready_confirm_sent, partner_confirmed, customer_rejected, relocated, at_partner_wh, at_own_wh_waiting`. There is **no `received`**. `received` is on `po_status` enum (`open / received / cancelled`), a different enum.

**Fix**: spec §5.3 + §7.8 changed to use:
- Sofa Reject path → `sup_status='at_warehouse_waiting'` (the new value from 0043)
- Normal path → `sup_status='delivered'` (matches existing 0034:938 which already uses this for full-receive)
- `po_status='received'` set only when all PO lines fully received (matches 0034:937, unchanged)

#### F4 — Storage policy uses `auth.app_role()` / `auth.app_partner_id()` (P0 schema)

§6.2 not edited in v2 round. Functions live in `public.*` schema (per 0002:18,36). Calling `auth.app_role()` from RLS policy → function not found → migration fails.

**Fix**: §6.2 storage policy now uses `(select public.app_role())` / `(select public.app_partner_id())`.

#### F5 — `stock_movements.po_id` does not exist (P0 schema)

0001:`stock_movements` columns: `id, sku, warehouse_id, qty, kind, ref, note, by_role, by_user_id, occurred_at`. **No `po_id`** — the link is via `ref` (text-typed PO id).

**Fix**: §6.6 `partner_sees_own_stock_movements` policy uses `stock_movements.ref` matched as text against `purchase_orders.id` (which is text typed per 0001:331).

#### F6 — `purchase_orders.order_id` does not exist (P0 schema)

0001:`purchase_orders` link to orders is `dl int references orders(dl)`. **No `order_id` column.** My §6.6 trigger references `NEW.order_id` → column undefined → migration fails.

**Fix**: §6.6 trigger drops `NEW.order_id` reference. The whitelist trigger doesn't need to compare `order_id` because `dl` (the actual link column) is also non-whitelisted — it's covered by `NEW.dl IS DISTINCT FROM OLD.dl` instead.

#### F7 — Trigger function marked STABLE; should be VOLATILE (P1 correctness)

`enforce_partner_po_column_whitelist` does business-logic enforcement that depends on session auth state. STABLE was cargo-culted from RLS-helper guidance.

**Fix**: §6.6 trigger function changed to `LANGUAGE plpgsql VOLATILE SECURITY DEFINER` (drop STABLE).

#### F8 — `0033 ost_partner_read` policy already exists (P0 dedup miss)

0033:96-107 has `ost_partner_read on order_supplier_threads` matching exactly what spec §6.6 `partner_sees_own_threads` proposes. v2 missed this dedup pass.

**Fix**: §6.6 drops `partner_sees_own_threads` policy. Net delta from 0046 reduced to 2 NEW policies (`partner_sees_own_stock_movements` + `partner_updates_rfd_fields` RESTRICTIVE).

#### F9 — Single `delivery_partner_id` reused for 4 different facts (P0 architectural)

Codex flags: same column means (a) procurement LP, (b) inbound pre-flight LP, (c) warehouse-owner proxy after Relocate, (d) customer-delivery LP. RFD reject clears it; relocate rewrites it; visibility depends on it. Different facts conflated.

**Fix v3 strategy**: keep single field in Chunk 1 BUT with strict invariants:
- `partner_reject_dispatch` does NOT clear `delivery_partner_id` — it only clears `request_for_delivery_at` + sets `partner_rejected_at`. The PO retains its LP assignment; Logistics may re-RFD or pick a new LP via DispatchPartnerDialog.
- `logistics_relocate_warehouse` rewrites `delivery_partner_id` ONLY when the new warehouse's `owning_partner_id` is non-null AND differs from current. This makes the column transition: (procurement LP) → (Relocate to LP-Y wh, copies LP-Y) → (LP-Y now owns this PO; HoOKkA delivers to LP-Y wh). The 4-uses simplify: `delivery_partner_id` always means "the LP currently tied to this PO", and Receive + customer dispatch consume that single value.
- Spec §C1.4 stays (Chunk 1 = single LP per PO across both legs after any relocate). The "4 different facts" critique is resolved by making the field semantically ONE fact: "the LP currently responsible for this PO".

True per-leg split (procurement_partner_id + delivery_partner_id) deferred to Chunk 2 §3, unchanged from v2 OQ3 closure.

#### F10 — C1.9 "no reason stored" conflicts with `partner_rejection_reason` column in 0044 (P1 spec internal contradiction)

C1.9 explicit: "LP Accept/Reject reasons = up to LP (not stored in system)". 0044 column list adds `partner_rejection_reason text`.

**Fix**: §6.4 drops `partner_rejection_reason` column. RFD Reject RPC accepts optional `p_reason` for logging only (audit_log entry text), not column persistence. Net 0044 column count: 5 → 4.

#### F11 — Signed-upload + Storage RLS muddled security model (P1 security)

If Hono signs with service_role token, Storage RLS doesn't apply (service_role bypasses RLS). If Hono signs with user JWT, Storage RLS IS the boundary. v2 spec implied both.

**Fix**: §6.2 + §8.6 commit to ONE model: **Hono validates caller role at API entry; uses USER JWT to call `supabase.storage.from('delivery-orders').createSignedUploadUrl()`; Storage RLS is the effective boundary.** No service_role for upload signing. Service_role used only for create-LP-account flow (§8.1).

#### F12 — "EXTEND existing 0034 RPCs" was under-scoped (P0 estimate)

`partner_confirm_receive` rewrite (per F1) is behavioral change, not slim role-check addition. Re-estimate: 4 NEW RPCs (was 4) + 1 NEW (`lp_accept_inbound_delivery`, was EXTEND) + 2 EXTENDED (was 3). Sprint 2 task list updated in §12.

### 6.1 Migration 0041 — `app_users.partner_id` integrity (CHECK + INDEX only)

> ⚠️ **Cross-check correction (§0.2)**: the `app_users.partner_id` COLUMN already exists since `0001_init.sql:141` and `public.app_partner_id()` already exists since `0002_rls.sql:36`. The drafted migration's column-add and function-definition are removed in v2 — keeping only the new CHECK constraint and partial INDEX as net delta.

```sql
-- 0041_app_users_partner_id_constraint.sql
-- Source: spec §3.4, supports C1.4 (per-LP-company tenancy via partner_id)
--
-- WHAT'S NEW (vs 0001/0002 baseline):
--   - CHECK constraint: role='partner' XOR partner_id IS NOT NULL invariant
--   - Partial INDEX: speeds "list users for a given LP company" queries
--
-- WHAT'S NOT HERE (already exists, not re-defined):
--   - app_users.partner_id column            (0001_init.sql:141)
--   - public.app_partner_id() helper          (0002_rls.sql:36)
--   - Auth Hook injects partner_id into JWT   (0004_auth_hook.sql:45,60)

-- Partial index for "list users for a given LP company" queries.
CREATE INDEX IF NOT EXISTS app_users_partner_id_idx
  ON app_users(partner_id)
  WHERE partner_id IS NOT NULL;

-- Integrity invariant: partner_id is NULL iff role <> 'partner'.
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'app_users_partner_id_iff_role_partner') THEN
    ALTER TABLE app_users ADD CONSTRAINT app_users_partner_id_iff_role_partner
      CHECK (
        (role = 'partner' AND partner_id IS NOT NULL) OR
        (role <> 'partner' AND partner_id IS NULL)
      );
  END IF;
END $$;
```

⚠️ **Constraint backfill caveat**: if any existing app_users row has `role='partner' AND partner_id IS NULL` (e.g. partial seed), the ALTER TABLE will fail. Pre-flight check + fix via `UPDATE app_users SET partner_id = ... WHERE role='partner' AND partner_id IS NULL` before the migration. Production today: 0 partner users exist (role is dormant), so constraint applies cleanly.

### 6.2 Migration 0042 — DO Storage bucket + RLS

> ⚠️ **v3 fixes (Codex F4 + F11)**: helper functions are `public.app_role()` / `public.app_partner_id()` (NOT `auth.*`). Security model commits to user-JWT signing — Hono validates caller role at API entry, then calls Supabase Storage with USER JWT (Storage RLS is the boundary). No service_role for upload signing.

```sql
-- 0042_storage_dos_bucket.sql
-- Source: C1.2 (PDF/JPG/PNG, 10MB), §8.6 storage path schema
-- Apply via Supabase MCP (mcp__supabase__apply_migration) which runs as service_role
-- — required for storage.buckets INSERT and storage.objects policy creation.
--
-- Bucket: 'delivery-orders'
-- Path: {po_id}/{uuid}-{do_number}.{ext}
-- RLS (user-JWT signing model — Hono uses user JWT to call createSignedUploadUrl):
--   - logistics + principal: read + write all DOs
--   - partner: read DOs where po.delivery_partner_id = own (own DO post-upload)
--   - dealer / supplier: no access (no INSERT, no SELECT)
--
-- DO upload happens at Receive time, performed by Logistics, NOT partner.
-- Partner reads DO for visibility only ("did Receive happen?"). They cannot upload.
-- This collapses the v2 spec confusion (which had partner write during pickup_assigned/
-- dispatched states — that was for customer-POD, but Chunk 1 is supplier-DO only.
-- Customer POD upload by partner = Phase 6 or Chunk 2 separate work.)

INSERT INTO storage.buckets (id, name, public)
VALUES ('delivery-orders', 'delivery-orders', false)
ON CONFLICT (id) DO NOTHING;

-- Read policy (logistics + principal full; partner own-PO; dealer/supplier denied)
DROP POLICY IF EXISTS "delivery_orders_read" ON storage.objects;
CREATE POLICY "delivery_orders_read" ON storage.objects FOR SELECT
TO authenticated
USING (
  bucket_id = 'delivery-orders' AND (
    (select public.app_role()) IN ('logistics', 'principal')
    OR (
      (select public.app_role()) = 'partner'
      AND EXISTS (
        SELECT 1 FROM purchase_orders po
        WHERE po.id = split_part(name, '/', 1)  -- po.id is text type, no cast needed
          AND po.delivery_partner_id = (select public.app_partner_id())
      )
    )
  )
);

-- Write policy (logistics + principal only — DO is supplier-side artifact, uploaded
-- by Logistics on Receive; partners do NOT upload supplier DOs)
DROP POLICY IF EXISTS "delivery_orders_write" ON storage.objects;
CREATE POLICY "delivery_orders_write" ON storage.objects FOR INSERT
TO authenticated
WITH CHECK (
  bucket_id = 'delivery-orders'
  AND (select public.app_role()) IN ('logistics', 'principal')
);

-- No UPDATE / DELETE policy — DOs are immutable post-upload (audit trail).
-- Cleanup TTL via storage retention policy (carry-forward `phase-4.5-do-storage-retention-policy`).
```

Filename sanitization: client-side reject filenames with `/`, `..`, control chars, or non-ASCII before signing. Rely on Storage's UUID prefix in path (`{po_id}/{uuid}-{do_number}.{ext}`) for collision avoidance.

### 6.5b Migration 0047 — orders_rollup_stage amend (NEW per Codex F2)

```sql
-- 0047_orders_rollup_stage_amend.sql — Phase 4.5 Chunk 1
-- Source: Codex outside-voice review F2 (2026-05-05)
-- Why: original 0036 rolls thread.logistics_stage='waiting' up to order
--   logistics_stage='dispatched'. That assumed waiting = post-relocate
--   forward-progress. Loo's NEW Sofa flow says waiting = at_warehouse_waiting
--   = stock at wh waiting for customer date = NOT yet dispatched.
-- Fix: drop 'waiting' from the dispatched-rollup set; keep it in ready_to_dispatch
--   set so order surfaces as ready_to_dispatch (not falsely dispatched).
-- The PO-level 'at_warehouse_waiting' filter (via 0043 enum value) is what
-- Logistics page uses to surface the waiting state — order rollup stays clean.
--
-- Idempotent: CREATE OR REPLACE FUNCTION (matches 0036 pattern).
-- Trigger from 0036:188 references this function name; no trigger change needed.

CREATE OR REPLACE FUNCTION public.orders_rollup_stage(p_order_id uuid)
RETURNS logistics_stage
LANGUAGE sql STABLE AS $$
  WITH t AS (
    SELECT logistics_stage
      FROM order_supplier_threads
     WHERE order_id = p_order_id
  )
  SELECT CASE
    WHEN NOT EXISTS (SELECT 1 FROM t)
      THEN 'placed'::logistics_stage
    WHEN (SELECT bool_and(logistics_stage = 'delivered') FROM t)
      THEN 'delivered'::logistics_stage
    -- v3 amend: drop 'waiting' from the dispatched set (was in original 0036).
    WHEN (SELECT bool_and(logistics_stage IN ('dispatched', 'delivered')) FROM t)
      THEN 'dispatched'::logistics_stage
    -- v3 amend: 'waiting' stays in this set — at_warehouse_waiting orders surface
    -- as ready_to_dispatch at order level, with PO-level filter for the queue.
    WHEN (SELECT bool_and(logistics_stage IN ('ready_to_dispatch', 'dispatched', 'delivered', 'waiting')) FROM t)
      THEN 'ready_to_dispatch'::logistics_stage
    ELSE 'awaiting_logistics_action'::logistics_stage
  END;
$$;

-- Permissions unchanged from 0036.
```

```sql
--    policy can't compare OLD/NEW column-by-column, but a trigger can).
--    VOLATILE per Codex F7 — trigger enforcement that raises on column changes
--    cannot be marked STABLE (planner could elide calls).
--    NOTE: purchase_orders schema (0001:329-348) has columns:
--      id, dl, supplier_id, warehouse_id, status, sup_status,
--      delivery_partner_id, expected_ready_date, pickup_date, eta_date,
--      customer_rejection, pay_status, placed_at, created_at, updated_at
--    Plus 0030 additions:
--      ready_confirm_at, partner_confirmed_at, do_file_path, do_uploaded_at,
--      do_uploaded_by, outsource_partner_name, outsource_partner_contact,
--      outsource_partner_zones
--    Plus 0044 v3 additions (this Chunk):
--      confirm_delivery_date, request_for_delivery_at, partner_accepted_at,
--      partner_rejected_at
--    LP whitelist (4 columns):
--      partner_accepted_at, partner_rejected_at, confirm_delivery_date,
--      AND ALSO `customer_rejection` jsonb (RFD reject path stamps it)
CREATE OR REPLACE FUNCTION public.enforce_partner_po_column_whitelist()
RETURNS trigger LANGUAGE plpgsql VOLATILE SECURITY DEFINER SET search_path = public, pg_temp AS $$
BEGIN
  -- Only enforce for LP role; internal roles bypass.
  IF (select public.app_role()) <> 'partner' THEN
    RETURN NEW;
  END IF;

  -- Reject any change to non-whitelisted column.
  -- NOTE: purchase_orders has `dl` (link to orders.dl), NOT `order_id`. Per Codex F6 fix.

     (NEW.dl                       IS DISTINCT FROM OLD.dl)                       OR
     (NEW.supplier_id              IS DISTINCT FROM OLD.supplier_id)              OR
     (NEW.warehouse_id             IS DISTINCT FROM OLD.warehouse_id)             OR
     (NEW.status                   IS DISTINCT FROM OLD.status)                   OR
     (NEW.sup_status               IS DISTINCT FROM OLD.sup_status)               OR
     (NEW.delivery_partner_id      IS DISTINCT FROM OLD.delivery_partner_id)      OR
     (NEW.expected_ready_date      IS DISTINCT FROM OLD.expected_ready_date)      OR
     (NEW.pickup_date              IS DISTINCT FROM OLD.pickup_date)              OR
     (NEW.eta_date                 IS DISTINCT FROM OLD.eta_date)                 OR
     (NEW.pay_status               IS DISTINCT FROM OLD.pay_status)               OR
     (NEW.ready_confirm_at         IS DISTINCT FROM OLD.ready_confirm_at)         OR
     (NEW.partner_confirmed_at     IS DISTINCT FROM OLD.partner_confirmed_at)     OR
     (NEW.do_file_path             IS DISTINCT FROM OLD.do_file_path)             OR
     (NEW.do_uploaded_at           IS DISTINCT FROM OLD.do_uploaded_at)           OR
     (NEW.do_uploaded_by           IS DISTINCT FROM OLD.do_uploaded_by)           OR
     (NEW.outsource_partner_name   IS DISTINCT FROM OLD.outsource_partner_name)   OR
     (NEW.outsource_partner_contact IS DISTINCT FROM OLD.outsource_partner_contact) OR
     (NEW.outsource_partner_zones  IS DISTINCT FROM OLD.outsource_partner_zones)  OR
     (NEW.request_for_delivery_at  IS DISTINCT FROM OLD.request_for_delivery_at)
  THEN
    RAISE EXCEPTION 'LP can only update partner_accepted_at, partner_rejected_at, confirm_delivery_date, customer_rejection (RFD reject)'
      USING ERRCODE = '42501', DETAIL = 'lp_column_whitelist_violation';
  END IF;

  RETURN NEW;
END;
$$;

DROP TRIGGER IF EXISTS partner_po_update_whitelist_trg ON purchase_orders;
CREATE TRIGGER partner_po_update_whitelist_trg
  BEFORE UPDATE ON purchase_orders
  FOR EACH ROW EXECUTE FUNCTION public.enforce_partner_po_column_whitelist();
```

## 11. SOP_SOFA_SPECIAL v2 (TS module rewrite — same-(from, rpc) bug fixed)

> ⚠️ **Cross-check correction (§0.6)**: drafted v1 had two transitions with same `(from='awaiting_logistics_action', rpc='logistics_receive_po_with_do')` differing only by reject-vs-normal branch. SOP module currently keys transitions on `(from, rpc)` (see `sops.test.ts:87` — `every transition.rpc is a non-empty string` and DAG check). **Two transitions with same (from, rpc) but different `to` makes the SOP module non-deterministic.** Fix in v2 below.

### 11.1 Decision: SOP module is **advisory documentation**, not authoritative state machine

The runtime branch (Sofa-normal vs Sofa-reject-relocate) is decided by the receive RPC reading **previous** PO `sup_status`:
- previous `sup_status = 'relocated'` → thread `waiting`, PO `at_warehouse_waiting`
- else → thread `ready_to_dispatch`, PO `received`

The SOP module documents allowed `(from → to)` pairs but **does not promise determinism from `(from, rpc)` alone**. `sops.test.ts` is updated to drop the implicit "rpc uniquely identifies destination" assumption.

Alternative considered: split `logistics_receive_po_with_do` into two RPCs (`_normal` and `_relocated`) so `(from, rpc)` is unique. Rejected because:
- One UI button (Receive) calls one Hono route — splitting RPC just pushes the branch into Hono
- Postgres RPC dispatch by branch on `sup_status` is cleaner than client-side picker
- Fewer RPC names to maintain

### 11.2 New SOP_SOFA_SPECIAL definition

Replace `packages/shared/src/sops.ts` SOP_SOFA_SPECIAL definition:

```typescript
export const SOP_SOFA_SPECIAL: SopDef = {
  name: 'SOFA_SPECIAL',
  stages: ['awaiting_logistics_action', 'ready_to_dispatch', 'waiting', 'dispatched', 'delivered'],
  // Transitions are advisory: (from, to, rpc) tuples document allowed paths.
  // Two transitions sharing (from, rpc) with different `to` is intentional —
  // the receive RPC branches on previous PO sup_status (relocated → waiting,
  // else → ready_to_dispatch). Keeps RPC dispatch consistent with one UI button.
  transitions: [
    // LP Accept happy path: previous sup_status was ready_confirm_sent or partner_confirmed
    { from: 'awaiting_logistics_action', to: 'ready_to_dispatch', rpc: 'logistics_receive_po_with_do' },
    // LP Reject + Relocate path: previous sup_status was 'relocated'
    { from: 'awaiting_logistics_action', to: 'waiting',           rpc: 'logistics_receive_po_with_do' },
    // Resume after customer reschedules
    { from: 'waiting',                   to: 'ready_to_dispatch', rpc: 'logistics_resume_from_waiting' },
    // Customer-delivery dispatch (RFD or Force)
    { from: 'ready_to_dispatch',         to: 'dispatched',        rpc: 'logistics_dispatch_customer_leg' },
    // Final delivery
    { from: 'dispatched',                to: 'delivered',         rpc: 'logistics_attach_pod_do' },
  ],
};
```

### 11.3 sops.test.ts updates

The DAG check (sops.test.ts:50-72) still passes because the graph IS a DAG (multiple edges between two nodes are OK). Tests to update:

- **Add**: explicit test that `awaiting_logistics_action → ready_to_dispatch` and `awaiting_logistics_action → waiting` both exist on `logistics_receive_po_with_do` for SOP_SOFA_SPECIAL, and that the runtime branch is RPC-side responsibility.
