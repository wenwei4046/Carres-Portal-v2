### 4.4 Global rules (横跨 3 种 SKU)

#### G1 · Procurement Tab UI 3-split (deferred to Chunk 2 — Chunk 1 keeps current single page)

```
├── Nice Future / Mattress    (factory_pickup flow)
├── HoOKkA / Bed Frame         (own_logistics, no LP pre-flight)

```

**Chunk 1 reality:** existing single LogisticsProcurement page handles all 3 with filter chips. The 3-tab split is FE rewrite scope = Chunk 2.

#### G2 · Order Rollup AND-rule (already enforced by 0036)

> Order's `logistics_stage = ready_to_dispatch` requires `bool_and(threads.logistics_stage in ('ready_to_dispatch', 'dispatched', 'delivered', 'waiting'))`.

✅ Cross-checked: implemented correctly in `orders_rollup_stage()` line 91-92.

#### G3 · Receive 全部 SKU 同模式 (C1.11)

按 Receive → stock_balances ↑ + 立刻 reserve for this order。Mattress / Bed Frame / Sofa 三家都一样。底层 RPC 共用 `logistics_receive_po_with_do` (in 0034); 修改 needed: Sofa Reject+Relocate 路径加 `at_warehouse_waiting` 分支。

#### G4 · Partner-Accept (RFD) vs Force-Dispatch (C1.14)

两种 leg（procurement pickup + customer delivery）都支持双路径：
- **A 路径 (RFD)**: partner 在 portal 看到请求 → Accept / Reject. State transitions through intermediate `request_for_delivery_at` flagged state.
- **B 路径 (Force)**: Logistics 直接 force-dispatch（跳过 partner accept）. State jumps directly to dispatched.

Both paths supported per leg, dispatch dialog has toggle.

#### G5 · 无 customer-direct 路径 (C1.6)

任何 SKU **都不能** supplier 直接 → customer。中间一定经过 warehouse（own 或 partner-owned）。

### 5.3 Data flow — Sofa LP Reject + Relocate

```
HoOKkA dispatches PO → po_sup_status: 'ready_confirm_sent', target wh = LP-X
LP-X sees Sofa in their portal "Inbound Pending" tab → clicks Reject Receive
   ↓ POST /api/logistics/pos/:id/lp-reject-inbound (RLS: caller is the LP-X partner OR logistics)
   ↓ RPC lp_reject_inbound_delivery: 
       UPDATE purchase_orders SET sup_status = 'customer_rejected'
       WHERE id = :id AND delivery_partner_id = caller's partner_id
       (also stamps customer_rejection jsonb with timestamp)
Logistics UI Procurement page → sees PO with sup_status='customer_rejected' → row shows "Request for Reassignment"
Logistics clicks Relocate → opens WarehouseRelocateDialog → picks new wh (own or LP-Y)
   ↓ POST /api/logistics/pos/:id/relocate-inbound { new_warehouse_id }
   ↓ RPC logistics_relocate_inbound_delivery:
       UPDATE purchase_orders SET warehouse_id = new_wh, sup_status = 'relocated', delivery_partner_id = (set per new wh ownership)
HoOKkA sees updated address → ships to new wh on planned date
Logistics receives at new wh → ReceivePOModal → DO upload → 
   ↓ RPC logistics_receive_po_with_do (modified):
       UPDATE purchase_orders SET sup_status = 'received', do_file_path = ...
       UPDATE order_supplier_threads SET logistics_stage = 'waiting' WHERE po_id = :id
       INSERT stock_movements (kind='in', qty positive)
       UPDATE stock_balances + reserve
       Set po_sup_status = 'at_warehouse_waiting' (the renamed value)
   ↓ Trigger orders_rollup_stage_after_thread_change fires →
       computes rollup: thread is 'waiting' → falls into rollup branch where waiting counts as dispatched-equivalent if ALL threads waiting+, else awaiting
Customer reschedules off-system → Logistics finds order in at_warehouse_waiting queue → clicks Resume to Dispatch
   ↓ POST /api/logistics/orders/:dl/resume-dispatch
   ↓ RPC logistics_resume_from_waiting:
       UPDATE order_supplier_threads SET logistics_stage = 'ready_to_dispatch' WHERE order_id = :order
   ↓ Trigger fires → rollup recomputes → orders.logistics_stage = ready_to_dispatch (if rollup AND-rule met)
Continues to Mattress-flow dispatch path (DispatchPartnerDialog → RFD or Force → Delivered)
```

## 6. Schema changes (additive migrations 0041-0046)

### 6.1 Migration 0041 — Partner role JWT claim

```sql
-- 0041_app_users_partner_id.sql
-- Source: spec §3.4, supports C1.4 (per-partner-company tenancy via partner_id)
-- Idempotent: ADD COLUMN IF NOT EXISTS

ALTER TABLE app_users ADD COLUMN IF NOT EXISTS partner_id uuid REFERENCES delivery_partners(id);

CREATE INDEX IF NOT EXISTS app_users_partner_id_idx ON app_users(partner_id) WHERE partner_id IS NOT NULL;

-- Auth Hook update needed (see §6.7) to inject partner_id into JWT app_metadata.
-- Helper function: auth.app_partner_id() reads from JWT.

CREATE OR REPLACE FUNCTION public.app_partner_id()
RETURNS uuid LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public, pg_temp AS $$
  SELECT (auth.jwt() -> 'app_metadata' ->> 'partner_id')::uuid;
$$;
GRANT EXECUTE ON FUNCTION public.app_partner_id() TO authenticated;

-- Constraint: a user can only have partner_id set if their role is 'partner'
DO $$ BEGIN
  IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'app_users_partner_id_iff_role_partner') THEN
    ALTER TABLE app_users ADD CONSTRAINT app_users_partner_id_iff_role_partner
      CHECK (
        (role = 'partner' AND partner_id IS NOT NULL) OR
        (role <> 'partner' AND partner_id IS NULL)
      );
  END IF;
END $$;
```

### 6.2 Migration 0042 — DO Storage bucket + RLS

```sql
-- 0042_storage_dos_bucket.sql
-- Source: C1.2 (PDF/JPG/PNG, 10MB), §10.3 storage path schema
-- Note: bucket creation may need supabase admin API, not pure SQL — see deploy notes

-- Bucket: 'delivery-orders'
-- Path: {po_id}/{uuid}-{do_number}.{ext}
-- RLS:
--   - logistics + principal: read all DOs
--   - partner: read DOs where po.delivery_partner_id = own
--   - partner: write DOs where po.delivery_partner_id = own AND status in (picked_up, dispatched)
--   - dealer / supplier: no access

-- Storage policy SQL (uses auth.uid + helper functions)
INSERT INTO storage.buckets (id, name, public)
VALUES ('delivery-orders', 'delivery-orders', false)
ON CONFLICT DO NOTHING;

-- Read policy
CREATE POLICY "logistics_principal_read_dos" ON storage.objects FOR SELECT
TO authenticated
USING (
  bucket_id = 'delivery-orders' AND (
    (SELECT auth.app_role()) IN ('logistics', 'principal') OR
    ((SELECT auth.app_role()) = 'partner' AND
      EXISTS (
        SELECT 1 FROM purchase_orders po
        WHERE po.id::text = split_part(name, '/', 1)
          AND po.delivery_partner_id = (SELECT auth.app_partner_id())
      ))
  )
);

-- Write policy (Logistics + Partner during their leg)
CREATE POLICY "logistics_partner_write_dos" ON storage.objects FOR INSERT
TO authenticated
WITH CHECK (
  bucket_id = 'delivery-orders' AND (
    (SELECT auth.app_role()) = 'logistics' OR
    ((SELECT auth.app_role()) = 'partner' AND
      EXISTS (
        SELECT 1 FROM purchase_orders po
        WHERE po.id::text = split_part(name, '/', 1)
          AND po.delivery_partner_id = (SELECT auth.app_partner_id())
          AND po.sup_status IN ('picked_up', 'dispatched')
      ))
  )
);
```

### 6.7 Auth Hook — JWT app_metadata claim injection

```sql
-- Auth Hook (Supabase Auth Hook function — runs on each token issue)
-- Inject partner_id into JWT app_metadata for partner role users

CREATE OR REPLACE FUNCTION auth.custom_access_token_hook(event jsonb)
RETURNS jsonb LANGUAGE plpgsql STABLE SECURITY DEFINER SET search_path = public, auth, pg_temp AS $$
DECLARE
  v_role text;
  v_partner_id uuid;
  v_dealer_id uuid;
  v_supplier_id uuid;
  v_claims jsonb;
BEGIN
  v_claims := event -> 'claims';

  SELECT role::text, partner_id, dealer_id, supplier_id
    INTO v_role, v_partner_id, v_dealer_id, v_supplier_id
    FROM app_users
   WHERE auth_user_id = (event ->> 'user_id')::uuid;

  IF v_role IS NOT NULL THEN
    v_claims := jsonb_set(v_claims, '{app_metadata,role}', to_jsonb(v_role));
  END IF;
  IF v_partner_id IS NOT NULL THEN
    v_claims := jsonb_set(v_claims, '{app_metadata,partner_id}', to_jsonb(v_partner_id));
  END IF;
  IF v_dealer_id IS NOT NULL THEN
    v_claims := jsonb_set(v_claims, '{app_metadata,dealer_id}', to_jsonb(v_dealer_id));
  END IF;
  IF v_supplier_id IS NOT NULL THEN
    v_claims := jsonb_set(v_claims, '{app_metadata,supplier_id}', to_jsonb(v_supplier_id));
  END IF;

  RETURN jsonb_set(event, '{claims}', v_claims);
END;
$$;
```

⚠️ **Note**: existing project may already have an Auth Hook (per CLAUDE.md §8 Fix 1). This function REPLACES the existing one; verify before applying. The hook must be configured in Supabase Auth settings via dashboard (not pure SQL).

## 10. Risk register

### 10.1 Auth Hook deployment risk

Replacing the Auth Hook function requires:
1. SQL migration creates new function
2. Supabase dashboard configuration sets the hook (NOT pure SQL)
3. New tokens issued after re-login include partner_id claim

⚠️ **Existing tokens** issued before deploy don't have partner_id. Mitigation: short token TTL (matches Supabase default 1h), users re-login after deploy.

10 MB max × N uploads → cost grows. Mitigation:
- Storage quota monitoring
- TTL or archive policy (deferred to carry-forward `phase-4.5-do-storage-retention-policy`)
- Path obfuscation via UUID (already in schema)

- Single endpoint `/api/principal/partners` POST
